## Milestone 2 — DONE: laptop-reachable flight controls through the real keymap

Design: a real-engine keymap seed, not preview-only control substitution.
`Src/OrbiterCore/metal/fixtures/laptop-keymap-lines.txt` rebinds exactly the
33 engine actions whose stock default base key exists only on the numeric
keypad (per `Src/Orbiter/Keymap.cpp` lkeyspec), using engine keymap.cfg
vocabulary and physically laptop-reachable base keys (main-row digits, H/J/K/L,
arrows, `/`, Insert/Home, with Ctrl layers for the LPRCS set). Engine semantics
untouched: bindings are parsed by the real `Keymap::Read`/`ScanStr`, consumed by
the real immediate/polling/buffered handlers.

Preview allowlist: `preview_keymap.h` + `main.mm` extend the bounded publisher
to exactly those physical scancodes (SDL->DIK via the existing owned table);
keypad, modifiers and Ctrl+P remain allowed; nothing else is added.

Shipped path: `package_preview.py` stages the seed as bundle resource
`keymap-seed.txt`; `preview_startup.h` copies it into each private session as
`keymap.cfg` before engine start. `Keymap::Read` applies listed labels over
`SetDefault()`, so unlisted actions keep engine defaults.

## Milestone 1 — DONE: unpause regression + real Lua support built in

User symptom (2026-10-15 handoff): unpausing produces weird behavior and
numerous error modals. Preserved evidence from the visible run
(`~/.hermes/cache/scratch/orbiter-overnight-20261016/Orbiter_core_metal.log`,
copied from `session-H1uKe5` before reruns) shows exactly one error class:

```
000000.823/.824 (x3): Could not find a module named LuaInline. Tried ./LuaInline.dylib and ./LuaInline/LuaInline.dylib.
000122.847 (x1): same message, during flight right after the unpause window
```

First failing engine boundary (source-backed): the DG vessel's script system —
`DeltaGlider::clbkInitScript` → `ScriptInterface::NewInterpreter` →
`LoadInterpreterLib` → `Orbiter::LoadModule(".", "LuaInline")` fails because
`LuaInline` (and `LuaInterpreter`) were never built or staged in the macOS core
spike. The DG subsystems retry interpreter creation when script callbacks fire
during unpaused flight, which matches "numerous errors after unpause". The
on-screen modal rendering itself was not captured as text; the log entries are
the proven error source, modal↔entry mapping remains inference (strong).

Fix, test-first as required:

1. `unpause_control_probe.h` + `--session-unpause-test` /
   `--session-unpause-ignore-test` in `main.mm`: the host applies real
   `Pause(true)` at startup, then a real buffered Ctrl+P command is published
   at frame 6. The probe reads `oapiGetPause()` and real sim-time advance per
   frame — proving pause semantics already work; the errors were the module
   class, not the pause path.
2. `unpause_regression.py` was run RED first (before the Lua targets existed):
   unpause oracle 30/30 PASS, module-load oracle FAIL with verbatim
   `Could not find a module named LuaInline...` — reproducing the user symptom
   in a bounded hidden session. Only then the fix:
3. Native `LuaInterpreter` + `LuaInline` dylib targets in
   `Src/OrbiterCore/modules/CMakeLists.txt` (upstream unmodified sources,
   `-undefined dynamic_lookup` like the vessel modules, `stage-native-lua`
   copies them to the **content root** because the engine script path is `.`
   and `Orbiter::LoadModule(".")` looks there). `LuaInline` carries
   `lua_inline_dependency_init.cpp` — the port-side equivalent of the SDK
   DllMain process-attach callback (`InitModule`/`ExitModule` via
   constructor/destructor, same seam as `celbody_dependency_init.cpp`).
4. Port compat shims the upstream sources need but the macOS build lacks:
   - `Src/OrbiterCore/shim/sync.h`: Win32 mutex/wait/thread primitives
     (CreateMutex/WaitForSingleObject/…) as a binary-semaphore implementation,
     required by the Lua interpreter's cross-thread handover; owner-bound
     mutex semantics deliberately avoided because release happens on a
     different thread.
   - `Src/OrbiterCore/modules/lua_xrsound_unsupported.cpp`: the upstream
     Interpreter ctor calls `LoadXRSoundAPI()` unconditionally while
     `lua_xrsound.cpp` needs the unported XRSound plugin (`XRSound.h`), so the
     port supplies the entry points with upstream's without-XRSound semantics
     (`xrsound.create_instance` → clean `luaL_error`).
   - `Src/OrbiterCore/modules/gccore_custom_camera_unsupported.cpp` +
     `Src/OrbiterCore/sdk_include/gcCoreAPI.h`: LuaInterpreter references the
     D3D9Client `gcCore` custom-camera import symbols; with no graphics client
     in the preview they resolve to port-side stubs behaving like a run
     without the client (SetupCustomCamera→NULL/nil, DeleteCustomCamera→-1/
     false, On/Overlay no-ops). Replace by binding a real gcCore interface
     when the Metal graphics client exists.
   - SDK headers: `INFINITE` and `__cdecl` no-op in `OrbiterPlatform.h`
     (upstream gets them from `<windows.h>`); `OAPI_MSGTYPE=LRESULT` on LP64
     macOS (mirrors the upstream `_WIN64` branch — 32-bit would break the
     SDK's pointer↔handle casts); `shim/windows.h` includes `sync.h`.
   - CMake force-includes `windows.h` for the two Lua targets (upstream
     expects it transitively; port keeps upstream sources untouched).
5. Rerun GREEN: `unpause_regression.py` exit 0 — 30 frames, real
   `oapiGetPause()` true→false at the Ctrl+P boundary, sim time advances only
   while unpaused, ZERO module-load errors, positive proof `Loading module
   LuaInline` in the engine log (LoadModule handshake), negative control
   (`--session-unpause-ignore-test`, key withheld) still fails and tears down.
6. Bundle acceptance: `preview-v4/OrbiterCorePreview.app` packaged with the
   staged dylibs, `preview_regression.py` 3× hidden lifecycles PASS, and all
   three v4 sessions' engine logs show `Loading module LuaInline` … clean
   unload, zero module errors. The DG's `run('dg/aap')` AAP interpreter path
   therefore now resolves through the real engine module loader.
7. No-regression sweep after the SDK header changes: rebuilt everything in the
   spike (clean), `orbiter-preview-keymap-tests` PASS (33 bindings),
   `laptop_regression.py` PASS ×3 + negative control,
   `preview_regression.py` PASS ×3 on v4.

Still not claimed: the modal↔log-entry mapping is inference, and the AAP
autopilot's *script behavior* (aap.lua logic running live) was not asserted
frame-by-frame; the regression asserts module load success + zero engine
errors, not AAP functionality. Lua custom cameras intentionally have no
graphics interface (no client yet).
